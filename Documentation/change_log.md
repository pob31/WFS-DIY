# Changelog

All notable changes to WFS DIY are documented in this file, organized by release tag (newest first). Sections marked "also tagged" note commits that carry more than one tag (e.g. a plugin-track tag and an app beta tag landing on the same commit). A leading **Unreleased** section, when present, collects work that has landed but not yet been tagged; it is renamed to the tag at release.

## v1.0.0beta45 — 2026-09-04

### Added
- **A stereo pair's image orientation can be locked, and the mouse wheel now aims it.** Two ways of shaping a stereo image that were missing on a machine with no touch screen and no Space Mouse.
  - **`inputStereoAxisLock`** (0/1, per channel, default off) drops the automatic tangential term entirely. With it on, the pair spreads along the fixed world axis turned by **Stereo Axis**, so that dial stops being a rotation applied to a reference that moves with the source and becomes an absolute bearing off house left/right — the image holds still while the source walks, which is the whole point. It has a toggle under the Axis dial on the Inputs tab, `/wfs/input/stereoAxisLock` with its `/remoteInput/` twin, an OSCQuery node, a QLab label, and it joins the existing **Stereo Image** snapshot scope group so a cue can recall it alongside width and axis. Deliberately **not** a rampable parameter: a boolean has no useful transition time. While the lock is on the axis follower is pinned to the locked orientation rather than left to go stale, so unlocking glides back onto the live tangential axis under the rate limit below instead of snapping to wherever the source has since travelled.
  - **`L` on the Map** toggles the lock for every selected stereo pair. A mixed selection converges rather than flipping each channel past the others: the target state is the inverse of the first one found. The key falls through when nothing stereo is selected, and `MainComponent::keyPressed` claims no `L` of its own, so it stays free everywhere else.
  - **The wheel turns the image axis** whenever stereo inputs are selected on the Map — 5° a notch, matching `WfsRotationDial`'s own wheel step, and 1° with Shift held, the same "Shift is the fine step" rule the arrow keys already use. The sub-degree remainder is carried between events, as the Space Mouse's is, because the parameter is an integer and a trackpad delivers a fraction of a notch at a time; rounding each event on its own would throw a slow scroll away entirely. **Ctrl/Cmd forces the zoom through**, so a selection that outlives the edit does not cost the wheel — Ctrl is otherwise only read on reverb drags, so nothing collides. Zoom is also still on right-drag, left+right drag, middle-click reset and pinch, and Escape clears the selection.
  - The DAW plugin suite does **not** reach the lock: a third Track parameter needs a `plugins-v*` release of its own.

### Changed
- **A channel's colour no longer disappears when the tile grid closes, and the Array and Cluster dropdowns now wear the colour they assign.** The colours that identify an input on the map and in the selector grid, and an array on the output tiles and the speaker membranes, were computed in six places and shown in none of the three places an operator actually works from: the collapsed channel-selector button in either tab header was plain, and the Outputs tab's **Array** and the Inputs tab's **Cluster** dropdowns were uncoloured even though the assignment they make is exactly what colours everything else. The collapsed button now carries the selected channel's own colour — its input hue on the Inputs tab, its array hue on the Outputs tab, and the tiles' dark grey for an output set to Single — and both dropdowns carry the selected index's colour, with every entry in the open list chipped in its own.
  - **Array and cluster colours stay derived, and stay unpickable.** They encode *membership* — which array an output belongs to, which cluster an input is in — rather than identity, so there is nothing for an operator to choose: the number decides the colour. Ten array hues are already close to the limit of what stays mutually distinguishable, and a free choice would have cost the one thing these colours are for. Nothing is stored for them, and the Android remote keeps recomputing the identical HSL formula on its own side rather than being told, so it cannot drift out of step. (Inputs *are* pickable — see below — because an input's colour is a label for a source, not a statement about grouping.)
  - **Arrays and clusters have always shared a palette** — `getArrayColor(n)` *is* `getMarkerColor(n, true)`, which is what the map's cluster markers and the Clusters tab's buttons use — so cluster 3 and array 3 are the same colour. That is pre-existing; putting both on coloured dropdowns only makes it visible. The two selectors are driven by one shared `Source/gui/ColouredIndexComboBox.h`, since both are the same "none, then 1-10" shape.
  - The tint lives in `ChannelSelectorButton` and reuses the `channelColorProvider` / `textColorProvider` the popup tiles were already given, rather than being restated per tab — so each tab's existing contrast rule carries over untouched and the **Reverb tab, which installs no providers, clears the overrides and renders exactly as before**. Refresh is the interesting part: an output's array can move without the selection moving (OSC, MCP, the Array Helper, a project load, undo — but *not* "apply to array", which does not carry `outputArray`), so `refreshChannelColour()` runs from `loadChannelParameters` **and** from the combobox's own edit path — the latter because `saveOutputParam` writes under the `isSelfWriting` gate, which suppresses the listener reload and would otherwise leave the tab's own edit unpainted. The Cluster box refreshes on the tracking-conflict revert too, which reverts with `dontSendNotification` and so never reaches `onChange`.
  - The dropdown rows are `PopupMenu::CustomComponent`s installed through `ComboBox::getRootMenu()`, carrying their label as the item title — `addCustomItem` stores it as `Item::text`, which is what `getItemText` / `setSelectedId` / `getText()` read, so selection and the TTS announcements are unchanged. They are stateless by construction: `showPopup()` copies the root menu on every open and `PopupMenu::Item`'s copy constructor *shares* the reference-counted component rather than cloning it, so the same instance is reused and anything cached at first paint would show a stale tick on the next open.

- **An input channel can now be given a colour of its own.** A round swatch in the channel selector's popup, between the title and the close button, opens a colour wheel; the chosen colour replaces the hue the app derives from the channel number, and does so everywhere that hue was used — the selector tiles and the collapsed selector button, the map marker and its live-source radius gradient, the stereo spread bar, and the patch matrix row. **Auto** puts a channel back on its derived hue. It lives in the popup rather than beside the collapsed channel button because that button is already painted in the channel's colour — a swatch next to it said the same thing twice — and because the grid is where every other channel's colour is visible to choose against. The grid stays open behind the wheel, and its tiles recolour as you drag. Output and cluster colours are deliberately untouched: they encode array and cluster membership rather than identity, so they stay fixed and unpickable.
  - **Stored as 24-bit RGB in a positive int, with −1 meaning auto** — not as an ARGB. `ValueTree::fromXml` types every property as a string and `WFSVar::toInt` resolves that through `String::getIntValue()`, a *signed* 32-bit parse, so an opaque `0xFF……` written back as unsigned decimal (up to 4.29e9) would not have survived a save: the exact "works when new, broken when saved" failure `VarCoercion.h` exists to warn about. Alpha is always opaque for a channel colour, so dropping it costs nothing and keeps the value inside a signed int, legible in the XML, and a natural int32 on the wire. −1 is the default, so every existing project and every untouched channel looks exactly as it did.
  - **It is identity, not show state.** `inputColour` sits on `<Channel>` beside `inputName`, is excluded from cluster propagation, and is listed as deliberately not snapshotted — so recalling a cue never repaints the rig, and a Shift-drag on a clustered channel cannot smear one colour across its siblings. That last one is load-bearing rather than tidy: `ClusterParamEdit` resolves anything numeric to *relative* mode, and `inputName` escapes only by being a String, so an INT without the exclusion would have offset every member's colour by the drag delta.
  - Reachable from OSC (`/wfs/input/colour`), OSCQuery, MCP and the tablet's `/remoteInput/inputColour`. **No `kRemoteProtocolVersion` bump**: the addition is additive and a v4 tablet drops unknown addresses at its catch-all, the precedent `sendRemoteChannelList` set. **WFS Control 2 follows it as of 1.0-beta_11**, on its map markers — the desktop sends the *stored* value, so the tablet keeps owning the −1 fallback and goes on deriving the hue for any channel that has no picked colour. There is no picker on the tablet: colours are chosen on the desktop and only mirrored.
  - **The black/white text rule was wrong, and free colours made it matter.** `getContrastingTextColor` switched to white below luminance 0.4, but the point where black and white contrast equally is 0.179 — so every mid-tone background got white at about 2.4:1 where black gives about 8.6:1. Corrected. Nothing moves; text flips from white to black on array/cluster tiles 6-10, roughly nine of the thirty-two derived input hues, and the matching patch-matrix cells, always in the direction of more contrast.
  - The patch matrix needed a repaint hook of its own: it reads row colours through a provider evaluated at paint time, but its ValueTree listener only branches on the patch data, so a colour change reached it with nothing to trigger a redraw. The map already coalesces its own repaint and the selector tiles are rebuilt on every open.

### Fixed
- **A stereo pair's image stopped following the source near the edge of the stage, then snapped to catch up.** The automatic spread axis is tangential to the origin→source bearing, which turns at `v/r` — undefined at the origin and sweeping 180° over a few centimetres near it. That was handled by holding the last axis computed outside a 1 m `kAxisFreezeRadius` disc, and the header argued the handover was continuous by construction. It is, but only for a **radial** approach and retreat. A source that drives *through* the disc enters at one bearing and leaves at the opposite one: inside, the image does not follow at all; at the exit boundary it snaps through the entire sweep at once. That is not the corner case it reads as either — `originDepthDefault` is `-stageDepth/2`, "downstage centre", so on a stage left at its default the disc sits at the **front edge**, exactly where performers walk.
  - `WFSStereoImage::followAxis()` replaces the hold with an angular **rate limit**: the axis chases the live bearing at no more than 360 °/s (7.2° per 50 Hz tick) on a *measured* interval, not a hardcoded 20 ms — a fixed step would under-rotate precisely when the message thread has stalled, which is when the anchor has moved furthest. Crossing the reference point now sweeps the image round over about half a second instead of jumping, and there is no longer any radius inside which it stops following.
  - **It costs nothing where it does not apply**, and that is load-bearing rather than an optimisation. When the target is within one step it is assigned *exactly* rather than routed through a `cos`/`sin` pair, so at any stage distance the axis is the same float a build with no limiter at all computes — which is what the width-0 null and the width-invariance sweep rest on. A source 5 m out moving at a brisk 3 m/s turns its bearing at 34 °/s, an order of magnitude inside the cap.
  - An **unprimed** follower, and an anchor that moved more than 1 m in a single tick (50 m/s — a recall, a project load, a flung drag at minimum zoom), snap instead of gliding: nothing travelled there, so there is no motion to smooth. The array is cleared on every render-source rebuild, which now means "snap on the next tick" rather than "reset to +X", so a reorder or a type flip no longer hands a pair the previous occupant's orientation. Do not reintroduce a hold on top of this: a held axis is a discontinuity waiting for an exit.
  - The self-test (`WFS_TEST_STEREO_GEOMETRY=1`) drops the two latch tests and gains four: the per-tick turn cap across a traverse through the origin, unit length across a limited sweep, bit-exact settling once clear, bit-exact agreement with an unlimited build at stage distances, both snap paths and their sub-threshold counter-case, and the locked axis being anchor-independent.
- **The stereo axis stuck at −179° instead of wrapping to +180°.** `wrapPhaseDegrees` passes anything already in `[-180, 180]` through untouched, because an LFO phase of −180 is a legitimate value — but `inputStereoAxisOffset` runs from −179, so the ValueTree write clamped the −180 straight back to −179 and a 1° decrement could never cross the boundary. A Space Mouse twist simply stopped there. New `wrapAxisDegrees` folds −180 onto +180 (they name the same bearing) and is used by the Space Mouse path, the map's two-finger rotation and the new wheel; `wrapPhaseDegrees` is left alone for the LFO.
- **The Outputs EQ's dials, sliders and value labels stopped following the EQ graph.** Dragging a band marker on the output EQ display moved the curve and the audio, but that band's frequency slider, gain and Q dials, shape box, toggle and its three value labels stayed where they were until the channel was reselected — so the numbers under the graph disagreed with the graph, and with what was being rendered. The reverb pre- and post-EQ displays were never affected. The cause was `ownerPersistsValue`, set on the output display in beta22 so that graph edits would route through `saveEqBandParam` and so reach the rest of an output array in relative mode — correct, but that write happens inside the `isSelfWriting` scope, which is precisely what tells `valueTreePropertyChanged` to skip the reload that refreshes the controls. The graph became the one edit path that persisted without ever announcing itself to the tab. The reverb displays leave `ownerPersistsValue` at its default, so `EQDisplayComponent` writes the band tree itself *before* any self-write scope exists and their reload still fires; that asymmetry is why only one of the three EQs showed it.
  - The per-band control update is now a named `refreshEqBandControls()` rather than a loop body inside `loadChannelParameters`, so the graph callback and a channel load cannot drift apart about what a band's controls should read. The graph refreshes **only the band that moved**, instead of queueing a full channel reload per drag event, and it reads the band back out of the ValueTree rather than trusting the value it was handed — so a relative array write displays the value that actually landed. It runs under `isLoadingParameters` for the same reason the load loop does: `WfsSliderBase::setValue` and `WfsBasicDial::setValue` both fire `onValueChanged`, and without the guard the refresh would write straight back into the tree it just read.
- **The Inputs tab's Array Attenuation dials kept greying out arrays that had just been populated.** The ten dials dim to alpha 0.3 for arrays no output belongs to, but `outputArray` is edited on the *Outputs* tab, and the Inputs tab only ever re-evaluated the dimming inside `setMutesVisible` — reached on a sub-tab switch or a channel load. Assigning outputs to an array therefore left that array's dial greyed until a different input was selected and the whole sub-tab was rebuilt, and emptying an array left its dial bright for just as long. The dimming is now its own `updateArrayAttenDimming()`, driven from the ValueTree listener on `outputArray` — the same seam that already re-runs the per-input feature warnings when a speaker capability changes on the Outputs tab, which had simply never been extended to the array assignment. It is coalesced behind a pending flag, because "Apply to array" and a config load both write `outputArray` once per output.

## v1.0.0beta44 — 2026-08-28

### Removed
- **Live Source attenuation on reverb feeds (`reverbLSenable`), and the vestigial `inputReverbSend`.** The feed toggle had a button on the Reverb tab's Channel Parameters, a Stream Deck key, an OSC address, an OSCQuery node and an MCP tool — and did nothing: the Live Source Tamer computes its gains per (input, *speaker*) from speaker positions, and the reverb feed matrix never read them (the engine's own comment said "reserved for future use"). Rather than extend the Tamer to nodes, it is dropped: a reverb node close enough to a live microphone to feed back is placed wrong, and the fix is to move it. The per-output `outputLSattenEnable` and everything on the input→output path are untouched. `inputReverbSend` was a dB send level with a `/wfs/input/reverbSend` address, OSCQuery bounds, a QLab label and a fuzz case, and no ValueTree writer — the send became a per-input toggle (`inputMuteReverbSends`) in July and every input feeds every node, shaped only by geometry. An old `reverbs.xml` carrying `reverbLSenable` loads cleanly: the attribute is stripped on load rather than carried along and re-saved.

### Fixed
- **The reverb was level-only matrixing in both directions; it is a real acoustic path now.** `WFSCalculationEngine` has always produced three matrices per direction — delay, level, HF attenuation — for input→reverb-feed and reverb-return→output, computed with the same geometry, the same minimal-latency alignment and the same Haas / system-latency / render-latency terms as the direct path. Only the **levels** were ever consumed. `ReverbFeedThread` summed a flat gain per (source, node); the return was one scalar `addWithMultiply` per (node, speaker). `getReverbOutputDelayTimesMs()` and `getReverbOutputHFAttenuationDb()` had **zero call sites anywhere in the repo**, and the input-side twins were read only by the Inputs > Visualisation sub-tab and the tablet mirror — so the GUI drew delay and air-absorption bars for reverb feeds that the audio never applied. Moving a source away from a node made it quieter and, if angular attenuation applied, narrower; it never made it arrive later or darker. Same class of defect as the beta35 output/reverb attenuation sliders that were "stored, editable via the GUI, and synced over OSC, but never read by the DSP engine".
  - **One cell, three sites.** `spatcore/dsp/AcousticTap.h` is the (smoothed fractional delay-line read → 800 Hz/Q 0.3 air-absorption shelf → level, accumulated) unit the direct path has always run per (input, output) pair, factored out of `InputBufferProcessor`'s inner loop. Three hand-copied fractional-delay reads is three places for the interpolation to drift apart. It is JUCE-free, so it is directly unit-testable, which is the other half of why it exists.
  - **Send**: `ReverbFeedThread` keeps a one-second delay line per source and a tap cell per (source, node), and taps at **device rate, before** the SR-ratio decimation so the fractional resolution is full. It parallelises across **nodes** — each worker owns one feed row and its own cell column, and the delay lines are written once before the sweep and read-only during it. The lines are fed even while pre-muted, so unmuting cannot replay stale history.
  - **Return**: new `spatcore/reverb/ReverbReturnProcessor.h`, the mirror image, parallelised across **output channels** rather than nodes — node-parallelism would need a scratch output buffer per node or race on the shared speaker buffer, and output-parallelism needs neither. Each node's wet block enters its delay line exactly where the old matrix took it: post node trim, post upsample, device rate, and **after** the `sharedReverbReturnBuffers` tap, so the binaural monitor's input is byte-for-byte unchanged. Post-mute pushes silence through the lines rather than skipping them, so lifting the mute cannot tap stale wet audio at a non-zero return delay.
  - **A cell whose HF damping is effectively zero skips the biquad** rather than running it at unity. That is not only the cheap path: it makes the result **bit-exact** against the plain gain matrix it replaced, which is what `testAcousticTapNullIdentity` asserts. `reverbHFdamping` defaults to 0.0 dB/m, so an untouched project changes only by the geometric delay it was always supposed to have.
  - **Cost.** The per-sample loop at the maximum configuration (32 nodes × 128 speakers = 4096 return cells) measured 5.9 ms per 256-sample block single-threaded against a 5.3 ms budget. A static source between 50 Hz matrix updates has a settled delay for nearly every block, and `DelayTargetSmoother::isSteadyFrom` now says so — conservatively, only once both the C1 transition zone and the delayed ramp have finished, so a yes means the general loop would have produced exactly that constant. The tap then walks the ring in contiguous runs at a fixed fractional offset: **5881 → 78 µs** at 32×128, **3555 → 97 µs** for the 104×32 send at 96 kHz. With air absorption on every pair the biquad's serial recurrence bounds it at 66 % single-threaded for 32×128, which the 4-way pool takes to ~17 %. The first cut of that run-walker read one sample late — a delay of 141.6 fetched the sample 140.4 back — and `testAcousticTapFastPathMatchesGeneral`, which holds the general loop up as the oracle at deliberately fractional delays, caught it at 0.017 of signal; it is 7e-6 now.
  - **What this makes audible, having been dead controls with full GUI, OSC, OSCQuery, Stream Deck and MCP surfaces:** `reverbHFdamping` (−6…0 dB/m on the send), `reverbDelayLatency` (±100 ms), `reverbMiniLatencyEnable` on both legs, `outputHFdamping` applied to the returns, and the input directivity and gradient-map HF offsets the engine already folded into the send HF. The Visualisation reverb rows and the Android remote's mirror of them become truthful rather than aspirational.
  - **Unchanged on purpose:** the GPU reverb backends (they implement the node-in/node-out `ReverbAlgorithm` contract; the feed and return matrices are CPU-side and above it), the binaural monitor (which was already the only path spatialising the returns, as HRTF point sources at their return positions), and all 15 CPU `offline-render` goldens — those drive the SDN/FDN/IR algorithms directly, below these matrices, and pass byte-identical.
  - **Not wired, and removed instead** — see *Removed* below for `reverbLSenable` and `inputReverbSend`.

## v1.0.0beta43 — 2026-08-27

### Added
- **The DAW plugin suite reaches a stereo input's width and axis, and finally says which channel an Input ID refers to** (also tagged `plugins-v0.0.5`). The plugin was the last surface still unaware of the app's stereo channels: `stereoWidth` and `stereoAxisOffset` had no automation lane in any DAW, and there was no way for the plugin to learn a channel's type — `inputChannelType` was published on no wire at all. Both Track parameters now exist on all five variants, exactly as Common Attenuation was rolled out: width in **metres** (0-50, default 4, the app's current law — not the 0-100 % it superseded), axis on the same rotary dial and the same -179/+180 range as Rotation.
  - **They are gated on the channel's type, at the send.** On a mono channel the section is not merely greyed but absent, and the editor shrinks back so a mono Track costs nothing it did not cost before. Hiding the controls would not have been enough on its own: a host automation lane keeps writing whatever the editor happens to show, so the outbound guard lives in the processor. This is the same defect the Stream Deck had when a displayed channel was retyped underneath it, in the one place where an automation lane makes it likelier rather than less.
  - **A Track now shows what its Input ID points at** — `#12 "Kick" (stereo)`, the app's own channel format, or `#7 - no such channel`. Channel numbers are permanent and deletions leave gaps, so a number *below* the channel count can still name nothing; the app drops those writes silently, which until now looked like a broken connection. Before the Master has actually read the app's channel list the line is blank: a plugin that has not been told anything says nothing rather than accusing a good channel of being absent.
  - Nothing about the plugin's **addressing** changed, and nothing had to: `/wfs/input/<n>/…` was always resolved by permanent number, never by index, so a saved DAW session has always kept pointing at the same channel across a reorder. The `1..64` range on Input ID is likewise still exactly the live number space — `addInputChannel` refuses a number above 64 on both its paths.
  - The Master learns the inventory from **one** OSCQuery request (`GET /wfs/input`) rather than a subscription per fact, refetched whenever the app reports `PATH_CHANGED`, and forwards it to each Track over the bridge. Two bridge entry points were added for the channel *name*, which is the only string on an interface where everything else is a double; they are **optional resolves and the ABI version stays 1**, following the ADM 3f precedent — `BridgeLoader` requires an exact version match, so a bump would reject every previously installed bridge outright instead of degrading. An older bridge simply yields no name.
  - Documentation: `WFS-UI_plugins.md` gains a section on what a permanent channel number means for a Track, including that **any Track output latches the app's numbering** — correct by design, since the plugin holds numbers, but it means a session a DAW has talked to never re-flows again. The shared-parameter table was also two entries out of date: it claimed 9 and omitted `commonAtten`, which shipped in beta35.

- **Shift is now the stereo image layer on the Space Mouse and on the map's second finger.** A stereo input's width and axis were reachable only from the Inputs tab dials and OSC; the two hardware gestures that already turn and lift a source had no way to shape its image. With Shift held, a Space Mouse twist rotates `inputStereoAxisOffset` and push/pull changes `inputStereoWidth` (push down to spread, pull up to narrow) while X/Y keep moving the source; on the map, a second finger placed near a touched stereo input with Shift held rotates the image axis and pinches the width instead of the directivity and height. Both apply only to stereo targets — on a mono input the two redirected axes do nothing rather than silently falling back to height and rotation — and neither touches the Clusters tab or the map's cluster-reference path. The map touch follows the live Shift state, as the Space Mouse does: pressing or releasing Shift mid-gesture switches layer and re-baselines the finger geometry on the current values, so height, width, rotation and axis can be adjusted back and forth without lifting the second finger. The map help card lists both gestures in every locale and grew to fit; it is now also clamped to the map height instead of running off a small window.
- **The Stream Deck+ can now reach a stereo input's width and axis, and stops driving them on a channel that is no longer stereo.** `inputStereoWidth` and `inputStereoAxisOffset` were reachable from the Inputs tab, OSC, the Space Mouse and the map, but not from the Stream Deck: its Inputs > Parameters page had no stereo awareness at all. The *Attenuation & Delay* section gains a fourth bottom-row key, **Stereo Parameters**, that swaps the two right-hand dials -- Distance Attenuation (or Ratio, under the 1/d law) becomes **Stereo Width** (±0.5 m per detent, ±0.1 m push+turn) and Common Attenuation becomes **Stereo Axis** (±5°, ±1° push+turn) -- and toggles them back off again. Attenuation Law stays live underneath: hiding a real parameter behind a display mode would be worse than a momentarily opaque key.
  - **Mono channels are untouched by construction.** The key is simply left unfilled there, and an unfilled binding is inert on every path (the key paints flat black, presses early-return, the refresh poll skips it), so a mono layout is byte-for-byte what it was. The mode flag is shared across channels like the Constraint/Flip flag beside it, and gated on the channel's type at both ends -- so it can be left on without ever showing through on a mono input.
  - The half that is a **fix**: nothing refreshed the Stream Deck when a channel's type flipped in place. `setChannel()` early-returns when the selected number has not moved, and the Inputs tab handled `inputChannelType` for its own controls only -- so retyping the displayed channel stereo -> mono would have left dials still bound to the stereo parameters, silently writing them onto a mono `<Input>` node. The tab now reports the changed channel's permanent **number**, and the Stream Deck rebuilds only when that is the channel it is actually showing and the Patch window does not own the surface. The number is what keeps a burst cheap: `inputChannelType` is written one channel at a time in a loop, so an unfiltered refresh would rebuild the page and push twelve images over USB HID once per channel on a stereo-count change or a config load.
  - The axis dial **clamps at -179°/+180° rather than wrapping**, unlike every other surface, which wraps via `wrapPhaseDegrees`. `DialBinding::applyStep` ends in a `jlimit` and the struct has no wrap mode, so this is the only behaviour reachable without changing spatcore; it matches the Stream Deck's own LFO Phase dial, which has the identical range and step shape. Width keeps its full 0-50 m range, which leaves its LCD bar reading low around the 4 m default -- the alternative put wide settings out of reach from the surface, and the exponential taper the GUI knob uses is unavailable here because `applyStep` guards it on a positive minimum.

### Fixed
- **`transition_seconds` is gone from the MCP surface, because nothing ever honoured it.** 44 tools advertised it and their descriptions promised "smooth interpolation", while the MCP dispatch has no ramper at all and jumped instantly. The CSV column it came from describes what the **OSC address** accepts, and the generator was copying that promise onto the MCP tool as well. Ramping stays an OSC capability — MCP round-trips are not timed tightly enough for a fade to mean much — so the honest answer is not to offer one.
- **`reverb_header_set_reverbs_map_visible` no longer demands a `reverb_id` it then ignores.** It is a Header-section display toggle stored on `Config/Master`; being in `WFS-UI_reverb.csv` earned it a channel argument it cannot use.
- **Sampler sets can be created and deleted over MCP, and are numbered from 1 like everywhere else.** The 17 `input_sampler_set_set_*` tools address a set by number, but there was no way to make one — `onAddSet` is a GUI button — so on a fresh input every one of them failed and stayed failed. New `input_sampler_create_set` / `input_sampler_delete_set` (tier 2, capped at 16 sets) close that; the defaults for a new set are read off a default-constructed `SamplerData::SamplerSet` rather than written out again, so they cannot drift from what the Sampler tab creates.
  - **The base mismatch is fixed.** The Sampler tab dropdown, the OSC `samplerSet` address and QLab cues all number sets from 1; MCP was the only surface counting from 0, so "set 1" meant different things depending which door you came through. `set_id` and `inputSamplerActiveSet` are both 1-based now and converted at the boundary. Existing MCP callers that passed 0-based set numbers need to add one.
- **The startup auditor stops drowning its own signal, and gained the check that matters.** It compared each tool's declared path against the live OSCQuery tree, but tools declare a channel-LESS path (`/wfs/input/attenuation`) while OSCQuery publishes channel-INDEXED ones (`/wfs/input/1/attenuation`) — so every per-channel tool read as drift: 354 of 383 "missing", the 20-line cap filled with false positives, and the few real ones never printed. Indexing the live set by its channel-stripped form as well takes that to 163.
  - Those 163 are then **reported as information, not error** — a correction rather than a softening. `internal_osc_path` is a convention string the generator synthesises and never validates against the router, whole namespaces (`/wfs/cluster`, `/wfs/network`) have no OSCQuery subtree at all, and an MCP call sends no OSC packet anyway. A missing path has never been why an MCP tool failed; it means the parameter has no OSC route, which matters to an OSC client and not to this one.

- **The ORTF (legacy) binaural mode aimed its virtual capsules the wrong way as soon as the listener was moved off the stage axis.** The two capsule POSITIONS rotated correctly with the listener's seat but their FACINGS were built from `-listenerAngle`, so the pair counter-rotated against the head it was strapped to — a pointing error of exactly twice the seat angle. It vanished at 0° and 180°, which is why it survived: those are the two angles anyone checks. Everywhere else the keystone pattern quietly ate the stage. A source at the stage origin measured 1.000/0.668 across the two capsules at 30° (a 3.5 dB pull to the left, where the correct geometry gives a flat 1.000/1.000 at every angle), the right capsule fell to 0.001 — effectively muted — at 67.5°, and at ±90° a centred source came out 7.7 dB down in both ears. Worse than the level error, the image could invert: at 90° a source 3 m to the listener's *right* rendered 14.7 dB louder in the LEFT channel. The delay cue was never wrong, because it derives from the positions — so the two cues actively fought each other, which is the kind of thing that sounds "off" without sounding broken.
  - This is the one change here that alters existing audio, and only in ORTF mode at a non-zero Orbit. The previous behaviour was a sign error, not a voicing, and there was nothing to preserve: the corrected geometry is rotation-invariant, so the stage now sounds the same from every seat, as it always should have.
- **Input level meters were dead whenever the WFS engine was not running, and froze rather than falling when it stopped.** Every branch of `LevelMeteringManager::updateLevels()` sourced input levels from a WFS processing *algorithm*, and the manager held no reference to the binaural renderer at all — so binaural-only monitoring, the exact case the binaural renderer exists for, showed nothing. The algorithm enum says which algorithm is *configured*, never whether one is *running*: it is a persisted user setting, no stop path clears it, and the algorithm pointers are addresses of member objects that are never null. So a stopped engine kept reading its idle detectors, either at −200 dB or frozen at the last pre-stop value, and the Map cannot tell either from silence.
  - An input level is a property of the **input**. It is now measured on `patchedInputBuffer`, per render source, from one helper called at the single point both audio paths share — right after stereo decomposition, in the WFS branch and the binaural-only branch alike. Post-patch, post-sampler, post-decomposition, so it sees sampler-driven preproduction and stereo slices, neither of which a hardware-side meter can.
  - The tap is a like-for-like *relocation*, not a new measurement — the algorithms' detectors read the very same samples one stage later. What changes is the envelope, deliberately: those detectors exist for the Live Source Tamer and carry a compressor's ballistics. Peak keeps its 100 ms release. RMS was a true 200 ms sliding window, and a one-pole matches a rectangular window of length T at τ = T/2 while converging to the identical steady-state value, so RMS is a **symmetric** 100 ms one-pole on the mean square — an instant-attack RMS would leap to near the peak on every transient.
  - Both taps now carry a per-block freshness stamp and report silence past 250 ms, substituted at read time so the message thread never races the audio thread's state. This also fixes the Input Patch header tint, which stayed lit at the last block's levels forever once the audio device closed.
  - Output levels and thread performance genuinely *are* per-algorithm, so they keep the switch — but they gained the not-running guard they were missing, or they freeze for the same reason.
  - Related: with processing on but no outputs patched yet, `OutputBufferAlgorithm::processBlock` returned on `outputProcessors.empty()` *before* notifying the input-analysis thread. That no longer affects metering, but it starved the **Live Source Tamer's** detectors, so gain reduction silently did nothing while a rig was being set up. The notify moved above the early return.
- **AutomOtion's audio trigger had the same root cause and is fixed with it.** It read input levels from the same idle algorithms, so level-triggered motion never fired in binaural-only mode. It now reads the shared input levels. Trigger ballistics shift slightly, since the new envelope is a display meter's rather than the tamer detector's.
- **A head tracker that blinked rotated the scene instead of holding it.** A webcam losing your face for 300 ms, or a dropped USB frame, made the renderer substitute the *manual* yaw/pitch/roll for that block. That was never a click — the ITD smoother and the shadow-coefficient ramp absorb the step — but it aimed somewhere else: with any non-zero manual yaw the whole room swung to a different heading and back on every hiccup. A selected tracker now holds its last good attitude; the manual angles are the fallback for "no tracker selected", which is what they mean.
- **`WfsRotationDial` ignored `setEnabled()` entirely.** `juce::Component::hitTest` never consults `isEnabled()`, and a bare Component does no disabled painting, so a dial its owner had disabled stayed at full brightness and fully draggable — the operator dragging the one control that still looked live in a greyed-out section. Both callers already assumed otherwise. It now dims and stops accepting input.
- The Listener Geometry panel's editors (Yaw/Pitch/Roll, Listener X, ear height, head radius) never got the numeric-editor setup every other field in the tab receives, so they had no input filter and no select-all-on-focus: clicking a Yaw field showing `0` and typing `45` produced `450`, which clamped to 180 — a half-turn from a keystroke that looked correct.
- The Orbit dial truncated toward zero instead of rounding, losing up to a degree on every write and leaving a 2°-wide dead band across 0 where the dot moved but nothing changed. The Stream Deck mirror of the same parameter already rounded.
- `binauralListenerX` was added to world X after the angular placement, so the "lateral" offset was only lateral at Orbit 0 — at 90° it moved the listener fore/aft instead of sideways, and at 180° it moved them to their left. It now rides the listener's own right-ear axis at every seat.

### Changed
- **"Listener Angle" is now "Orbit", because that is what it does.** It was the only rotation-shaped control in the binaural panel and it was documented as *"horizontal rotation of binaural listener view"* — but it is a **seat placement**: it moves the listener around a circle of Listener Distance about the stage origin, and they face the origin from wherever it lands. The scene never rotates. What changes is the distance to every source, and with the HRTF distance law clamping at 1 m that is worth up to +14 dB, landing differently on every source. Turning it read as the renderer misbehaving — "something happens but it mostly makes things much louder" — which is exactly right when you have been walked into the middle of the band and nothing on screen says so. The stored parameter, its id and its OSC path are unchanged; the label, the help text and the MCP tool description now describe the orbit honestly, and the MCP description no longer promises fractional degrees it never supported.
- **A Head Yaw dial sits beside Orbit**, driving the manual yaw that actually turns the head on the spot. Yaw is seat-relative — 0 faces the origin from any seat, which is also what a tracker's Set Zero establishes — so turning Orbit re-aims a tracker's zero along with the seat, and the help text now says so. While a tracker is active the dial mirrors the tracked yaw and is locked: a tracker *replaces* the manual yaw rather than offsetting it, so leaving the dial draggable would let the operator fight a control that cannot win. Mirroring it also gives the panel a second, far more legible sign that tracking is alive; until now only a small text readout moved.
- **The Orbit dial reads like the Map**: 0° at the bottom — the audience side, where Orbit 0 actually seats you — running counter-clockwise, instead of 0° at the top running clockwise. This is opt-in per dial; the LFO phase, input phase and stereo axis dials keep the default, since a phase has no plan view to agree with.
- **The Map draws the binaural listener** as a head glyph with a facing indicator, dimmed when the renderer is off. Nothing on screen used to show where the listener was, which is most of why moving them read as a malfunction. The glyph also makes a tracked head turn visible, and shows the listener translating on a legacy↔HRTF switch (legacy pins ear height at 1.5 m and ignores the sideways offset). Its position and facing come from a shared `WFSBinauralListener` helper so the Map can never draw a listener the renderer is not rendering — the same reasoning, and the same shape, as `StereoImageGeometry`.
- **ORTF (legacy) mode no longer holds the webcam.** That mode's renderer returns before head orientation is read at all, but the tracker selection was resolved with no reference to the render mode — so selecting the webcam and switching to legacy left the camera open, LED on and unavailable to other applications, with zero effect on the audio. The persisted selection is untouched, so the tracker re-engages on the way back to an HRTF mode.

## v1.0.0beta42 — 2026-08-18

### Added
- **Snapshots can be recalled from a MIDI keyboard or pad controller.** The input device is chosen in *Audio Interface ▸ Device Settings*; the channel and note are bound per snapshot in its Scope window; a note-on **above velocity 64** recalls it through the same scope-aware path as the *Reload Snapshot* button and `/wfs/input/snapshot/load`. Velocity ≤ 64, note-offs and velocity-0 note-ons are ignored outright rather than given a second meaning — a second gesture on the same key is a trap in a show, where the only thing that matters is that a firm hit fires the cue and nothing else does. A held pad or a MIDI echo cannot fire the same note twice inside 250 ms; when two *different* bound notes land inside one 5 ms tick the later wins, because a recall costs tens of milliseconds and queueing them would make the app chase cues the operator has already moved past.
  - *Why the binding lives on the `<InputSnapshot>` **root*** rather than inside `<ExtendedScope>`: it makes "who owns note 60" an outer-element XML parse — a few hundred bytes per file regardless of snapshot size — instead of a full read of every snapshot's channel data, which is what funds the live conflict check while you type. It also keeps notes out of scope **templates** for free, since those share the scope serializer; otherwise a template would hand the same note to every snapshot built from it. And it makes the binding follow the file: copy, rename or restore a snapshot and its note comes with it, where a project-level table would need a hook on each of those and still could not see a rename done in Explorer.
  - *Why the listener lives in `MainComponent`* and not in the Audio Interface window, which has been stopped-only since beta41 — a listener owned by that window would be absent during a show, the only time this feature matters. The window owns the selector; `MainComponent` owns the port and the index. For the same reason the trigger owns its `juce::MidiInput` directly instead of going through `AudioDeviceManager::setMidiInputDeviceEnabled`, whose selection is replayed only on the device-state fast path: the `openNamedDevice` fallback never calls `initialise()`, so MIDI would have died on exactly the launches where the audio device failed and the show most needs to keep running. MIDI recall works with no audio device open at all.
  - *Why the MIDI thread never touches the app*: a velocity test, one relaxed load from a 16×128 atomic table and one store of a packed key. No `callAsync` allocating on a high-priority thread, no captured `this` to outlive anything — the existing 200 Hz timer polls the parked key and does the work on the message thread.
  - The device selection is machine-local and remembers **identifier and name**, because a MIDI identifier's format is the OS's and is not promised stable across reboots. An unplugged device stays listed as "(not connected)" rather than silently reverting to Off, and re-opens itself when it returns — including across a restart, since the selection lives in `WFS-DIY.settings` and not in the audio device blob.
  - A channel+note already claimed by another snapshot is **refused**: the *Update Snapshot Scope* button is withheld and a red label names the owner. A collision that arrives on disk instead — a copied file, hand-edited XML, a restored backup — cannot be refused, so it resolves first-wins in file-name order (deterministic and identical on every machine) with a logged and status-bar warning naming both.
  - **The connection is snapshot recall and nothing else**, which the UI says outright — the selector is labelled *"MIDI snapshot recall:"* and its tooltip leads with "Snapshot recall only". The port is opened for input alone, the app never sends to it, and the only messages it acts on are note-ons that recall a snapshot; everything else falls through. ROLI Lightpad Blocks keep their own independent connection and are unaffected (a Lightpad's port does appear in the selector and should not be chosen — on Windows a MIDI port cannot be opened twice).
  - Bindings are for **input** snapshots only. MIDI Learn, Program Change and MIDI Show Control are deliberately out of scope; the trigger is shaped so Learn drops in later without changing anything else.

Pressing *Load* twice in a row was impossible without reopening the dropdown. They now test `getSelectedId() <= 1`, which needs no string at all and cannot drift from the localisation table.

### Changed
- **There is now one snapshot recall path instead of two.** The Inputs long-press and the OSC address had drifted apart — the OSC one validated the project folder and the snapshot name and refreshed the Inputs tab twice; the UI one used a per-tab scope cache and validated nothing. Both now call `MainComponent::recallSnapshotByName()`, which is also where the MIDI trigger lands rather than becoming a third copy. It is non-reentrant, because `ParameterDirtyTracker`'s suppression flag is a plain bool with no nesting counter and an inner release would mark the outer recall's remaining writes as operator edits. An externally-triggered recall now also moves the snapshot dropdown to what it actually loaded, so the operator can see which cue is live.
- **MIDI- and OSC-triggered recalls no longer create undo entries.** A cue-driven show would otherwise push one entry per cue and bury the operator's own edits under them. The mechanism already existed for MCP-origin writes — `getActiveUndoManager()` returning nullptr, which every write path already tolerates — and is now reachable as `spatcore`'s `TreeParameterStore::ScopedUndoSuppression`. It has to be an explicit flag rather than an origin tag: a snapshot load opens its own `OriginTagScope { Snapshot }` internally, which replaces whatever the caller set, so by the time the writes happen the origin can no longer tell a MIDI recall from a button press. The *Reload Snapshot* button keeps its undo entry. `undo()`, `redo()` and `clearUndoHistory()` gained the null guards they had been missing.
- **The head tracker calibrates itself instead of waiting for you to press a button.** Set Zero used to perform a capture-instant full-pose tare, which was only ever as good as the wearer's posture at the moment they clicked, and did nothing about yaw drift afterwards. The tracker library's new `htk::Stabilizer` replaces it with continuous estimation, built on one observation: **body-frame gravity is invariant under any yaw manipulation** — drift, recenter, the firmware's rest yaw-hold — so it is the one signal that yaw bookkeeping provably cannot corrupt.
  - **Auto-level** derives the pitch/roll mounting tilt from a ~120 s average of body-frame gravity taken while the unit is worn, re-anchoring yaw on each refinement so the output never jumps. A **wear gate** decides when to trust it: worn heads show micro-motion (breathing, sway) where a desk is dead still, and a large gravity step reads as pick-up/put-down and immediately distrusts the estimate. That is what stops headphones parked at an angle from teaching a wrong level.
  - Mount **azimuth** is not observable from gravity — a puck twisted about vertical looks identical — so yaw still needs a human action. **Set Zero now means recenter (yaw only)**, which is the user-visible change: it can no longer bake in the pitch of someone who happened to be looking down when they pressed it. The head unit's new **double-tap** does the same thing without reaching for the mouse, which for a listener already wearing headphones is the better affordance.
  - **Auto-center is deliberately left off.** It would leak yaw toward the long-term mean heading, which suits a desk user facing a monitor but not a WFS scene, and the library's own default agrees.
  - `headtrackUsbWearThresholdDeg` joins the machine-local settings. It is the one constant the library ships explicitly unvalidated — a desk reads about 1e-3° and a worn head 0.05–0.5°, so the 0.02° default sits between them by estimate rather than measurement. Too high and auto-level never engages; too low and a desk looks worn. Exposed so it can be calibrated against real captures without rebuilding on three OSes.
  - The app log now reports worn / not-worn, auto-level engagement with the estimated mount tilt and confidence, and each double-tap. Those transitions are the readout the threshold is calibrated against, and a tap has no on-device feedback beyond an LED blip, so confirming it landed matters.
  - Picked up with the tracker submodule bump, which also brings two **additive** ORIENT flags (`REST`, `TAP`) and firmware drift machinery: a converged-bias definition, a five-condition rest gate, and a slew-limited yaw-hold servo that cancels residual rest drift without being able to eat a genuine head turn. Additive per the protocol's §1.9 contract, so no version bump and no change to the byte-exact test vectors.
- The synthetic `htgen` capture cannot exercise auto-level: it emits a pure yaw sweep with a constant gravity vector, so the wear gate correctly reports "not worn" and the estimator never engages. Discovery, routing, streaming and the tap path are exercised without hardware, but **auto-level and the wear threshold can only be validated on a real head unit**.
  - A later submodule bump carries the hardware tuning that came out of the first bench session, almost all of it firmware: the head unit's raw zero-rate gyro offset exceeded the fusion filter's rest veto, which had been permanently blocking rest detection, bias convergence and `BIAS_OK`. It is now captured at boot across a genuinely quiet second, since the unit is always in someone's hand right after a flash and a motion-polluted capture is worse than none. The measured sample rate also turned out to be 431.6 Hz rather than the nominal 416, a 3.7% scale error in the fusion.
  - Host-side that lands as one behavioural change worth knowing: **a detected tap and an applied recenter are no longer the same event.** A brisk hand jerk could fake a double-tap, so the action is now honoured only for a wearer who has been settled for about two seconds — donning headphones is a wear transition full of tap-like jostles — and is then deferred until the head stops moving, so "front" is never captured mid-swing. The tap is still counted and still reported either way, so the log now says *detected* rather than *recentred*, which is the only thing it can honestly claim.

## v1.0.0beta41 — 2026-08-17

### Added
- **The binaural monitor is now a real HRTF renderer.** The previous renderer was two virtual microphone capsules 20 cm apart at ±45° — an ORTF-ish delay-and-sum whose stereo image was essentially the 0.58 ms inter-capsule delay, with no head shadow, no elevation cues and no externalization. A **Render Mode** selector now offers three algorithms:
  - **ORTF (legacy)** — the existing code path, byte-for-byte. Old sessions load into it (a missing `binauralRenderMode` reads as 0) and sound identical by construction; it remains the null-test reference.
  - **Structural HRTF** — a parametric spherical-head model rendered per source in the head frame: Woodworth ITD on the existing fractional delay lines (smoothed by `DelayTargetSmoother`), Brown–Duda head-shadow filter with per-sample coefficient interpolation so head rotation cannot zipper, an elevation notch, and 1/r plus the familiar air-absorption shelf. Personalized via a **head radius** control; near-field correction was deliberately left out (sources sit metres away).
  - **SOFA file** — measured HRIRs through a custom uniform-partitioned convolver (one forward FFT per source feeds both ears; direction changes swap pre-FFT'd grid spectra with ~2.5° hysteresis and a one-block crossfade). `juce::dsp::Convolution` was evaluated and rejected — its background loader is built for occasional IR swaps, not per-block direction changes. SOFA sets are baked at load onto a uniform 5°×10° grid with **ITD extracted and HRIRs time-aligned** (interaural cross-correlation plus loud-ear onset split; threshold-only onset detection mis-splits the shadowed ear's creeping-wave pre-arrival), so both render modes share one smoothed-delay ITD path. Ships with the **SADIE II KU100** set — repacked losslessly from 36.3 to 10.6 MB (`tools/repack_sofa.py`: float64 kept because libmysofa's array reader requires it, shuffle+deflate does the shrinking; the IR data is bit-identical) — and user files import into `<project>/sofa/` through an IR-picker-style combo. Reads via vendored **libmysofa** + a zlib inflate subset (`Z_PREFIX`ed to coexist with JUCE's embedded zlib).
  - The HRTF modes add listener X offset and ear height, spatialised reverb (below), and head tracking (below). Everything new lives in **`spatcore/binaural/`** as an app-agnostic engine — per-source direction math deliberately *not* contorted toward HOA; XOA's SH-domain binaural is specified separately in that repo's `Documentation/hoa-binaural-handoff.md`.
- **Head tracking, with a webcam tracker you can use today.** Head *attitude* deliberately bypasses the damped parameter pipeline (tracking that lags the head by the position path's ~100 ms one-pole feels broken): the render worker reads the active `HeadOrientationSource` fresh every block through an `RtSnapshot` fast path, while listener *position* stays on the damped 50 Hz path. Manual yaw/pitch/roll parameters remain the fallback whenever no tracker is active or a tracker goes stale (300 ms without a pose slews back to manual).
  - The **Webcam** source is a per-OS plugin (`wfs_headtrack.dll` — the GPU vendor-plugin split applied to computer vision, so OpenCV never touches the app build) loaded through a **versioned, POD-only C ABI** (`spatcore/binaural/plugin/HeadTrackPluginApi.h`) that fixes the GPU ABI's documented stale-DLL trap. Inside: camera capture with a latest-frame mailbox (frames are dropped, never queued — queueing is accumulated latency), YuNet face detection (vendored 230 KB MIT model), and head angles computed **geometrically from the eye centers and nose tip** with the axes decoupled by construction — roll is the eye-line slope and nothing else, yaw/pitch are the de-rolled nose offset/drop. It is deliberately not a 5-point `solvePnP`: mouth corners are unreliable under facial hair (a nod read as *roll* on a bearded face), `SOLVEPNP_ITERATIVE` without a guess needs six points, and the naive canonical-face frame is improper against the camera frame (mirror solutions at yaw ≈ 180°). Robust to beards, glasses and headphones; ~30–50 ms motion-to-ear; constant biases die in **Set Zero** ("look at the stage, click" — matrix pre-multiplication, never per-angle subtraction, because rotations don't commute; unit-tested). A live yaw/pitch/roll readout under the tracker dropdown is the visible proof tracking is alive — by design no parameter control ever moves with the tracker. Built by `tools/headtrack/build-headtrack-plugin.ps1/.sh`, compile-checked on all three OSes in CI, staged by the Windows release build, shipped optional in the installer (`skipifsourcedoesntexist`, like the GPU plugins). The future USB IMU receiver plugs into the same dropdown, ABI and calibration.
- **The USB hardware head tracker is that second source.** A dongle enumerating as a USB CDC-ACM serial port receives 2.4 GHz ESB broadcasts from any number of nRF52840 head units and multiplexes them onto one stream; every tracker it hears becomes its own entry in the same dropdown, keyed **`usb:<id>`** from the head unit's factory-derived hardware ID — stable across power cycles, so the selection survives in the show file. The protocol, firmware and host client library live in a separate repository (`github.com/pob31/headtracker_v1`, GPLv3), pinned here as `ThirdParty/headtracker`; its five host sources and three protocol C files **compile into the app** the way `hidapi` does, rather than shipping as a second runtime-loaded plugin — unlike the OpenCV-bearing webcam plugin, that library is dependency-free C++17, so the plugin split would buy isolation nobody needs.
  - **Set Zero is a body-side tare, not the camera's.** The webcam pre-multiplies by the inverse of the captured attitude, which is right when what you are cancelling is the *camera's* placement relative to the stage — a world-side rotation. An IMU strapped to a headband carries a *body-side* mounting offset, so the tare has to compose on the other side of the product. Pre-multiplying here would be exact only at the capture pose and would conjugate every later rotation into the tilted mounting axes: under a 25° mount roll, a true 30° head turn would read about 28°, with residual roll. The two are not two implementations of one idea, and the shared smoothing path deliberately excludes the tare so the wrong one cannot be reached for.
  - The quaternion→angle conversion is derived rather than guessed. The tracker's frame (X forward, Y left, Z up, Hamilton, body→world) and the renderer's head frame (x right ear, y facing, z up) are the same physical triad relabelled, so they differ by one fixed change of basis `C = Rz(−90°)`, and `R_offset = CᵀR(q)C` reduces to a signed index shuffle. The equivalent statement — negate the source's Z-Y-X yaw and pitch, keep roll — is pinned as a **unit test** rather than used as the implementation, so the derivation stays checkable instead of becoming three sign constants nobody can re-verify.
  - The zero request is **timestamped**: pressing Set Zero while the dongle is unplugged would otherwise fire minutes later against whatever pose the wearer happened to hold, silently rotating the entire scene. The webcam avoids this only because stopping the camera clears its flag, and a dongle that streams before anything is selected has no equivalent stop.
  - The dongle runs **whenever it is present**, not only while a tracker is selected, because its stream is the only thing the tracker list can be built from. Orientation routing is lock-free over an append-only table; anything touching the source list marshals to the message thread first, since creating a source appends to the vector the render worker holds a pointer into. A tracker that goes quiet stays listed as disconnected rather than disappearing, so the selected object survives an unplug and simply resumes — and a persisted `usb:…` chosen while the dongle was absent re-engages when it returns (gated on an atomic null-check and rate-limited, because that tick runs at 200 Hz and the lookup compares by-value `juce::String`s).
  - **No hardware exists yet** — the firmware compiles but has never been flashed. The whole path is therefore exercised against a synthetic capture: point `headtrackUsbReplayFile` (machine-local, alongside `headtrackUsbEnabled` / `headtrackUsbPort` / `headtrackUsbSmoothingHz`) at a file produced by the library's `htgen` and the app replays it instead of opening a port, driving handshake, discovery and per-tracker streaming end to end. Sign validation against a real head, the motion-to-ear latency budget and the filter tuning all wait for silicon; those constants carry `TODO(hardware)` markers. Smoothing defaults an order of magnitude lighter than the webcam's: 1.5 Hz suits landmark jitter and costs ~106 ms of group delay at rest, which on a fused IMU would make the hardware tracker feel *worse* than the webcam it replaces.
  - Two library-level defects were found and fixed upstream in the process. Quaternion normalisation guarded with `n2 < ε`, which is **false for NaN**, so a frame that passed CRC but carried a non-finite float propagated straight through — and the obvious repair to positive logic still let *infinity* past, because an infinite component makes the squared norm infinite, which clears a lower bound and then yields `inf × (1/√inf) = NaN`. Separately, the bench found that with the puck flat and Set Zero pressed, rolling it onto its side read as a yaw/pitch/roll mixture instead of pure roll: the rotation since capture was being expressed in the fusion's world basis, whose horizontal axes are an arbitrary 6DoF yaw origin. Boresight now re-expresses it in the capture-aligned frame, so Set Zero decomposes into the wearer's axes.
- **The reverb finally reaches headphones.** The binaural monitor used to tap only the dry input rings — reverb was simply absent from the mix it previewed. Node returns are now tapped post node-trim into multi-consumer rings (the SPSC node rings cannot be double-read) and rendered as additional sources at their **return positions**, giving depth on headphones. Studio-preview only — any solo mutes the tap, since a node carries a mix of every input feeding it — and balanced by a dedicated `binauralReverbAttenuation` (−40…+12 dB), because the headphone-appropriate wet level differs from what a room needs through speakers.

### Fixed
- **The update checker would never have offered the first stable release to a beta user.** A version segment's beta suffix is parsed into an int with a release encoded as the sentinel `-1`, and the comparison used that sentinel directly — so `1.0.0` versus `1.0.0beta41` compared `-1 > 41`, concluded the release was *older*, and reported "up-to-date". The comment directly above the line stated the intended rule ("a release beats any beta number"), so this was a straightforward inversion rather than a design disagreement. It is broken symmetrically: a release user would also have been offered a beta as an upgrade. Beta-to-beta ordering was always correct, which is why nine months of beta releases never surfaced it — the defect only bites at the boundary this project has not yet crossed. Releases are now ranked above every beta.
  - Worth recording for whoever cuts 1.0.0: the fix has to ship **in a beta**, not in the stable release. Beta41 users run their own copy of the checker, so a fix delivered only in 1.0.0 could not tell them 1.0.0 exists. Landing it here means beta40 users are offered beta41 by the old (correct in that direction) comparison, and every beta41 user then sees the stable release normally.
- **A degenerate face box snapped the listener's head to "straight ahead", and could poison tracking permanently.** The estimator's guard was `if (eyeDist < 1.0f) return;`, which does not catch a NaN eye distance — every comparison with NaN is false — so a degenerate detection sailed past it and emitted NaN angles. Worse, the angle helper returned `void`: a frame it rejected left the angles at their defaults while the caller still stamped the pose valid, so a lost face read as a confidently level, forward-facing head rather than as no tracking. Landmarks are now finite-checked, the distance test is positive-logic, the angles are validated before they are written, and the helper reports whether it succeeded.
  - The app-side source now drops non-finite poses **at the ABI boundary, before the zero capture and the smoothing filters**. The publish choke point would keep them off the render thread either way, but by then the calibration matrix and the 1-Euro state would be latched non-finite and tracking would never come back — the filters carry their history forward forever. So this guard is about *recovery*, not just safety; a second check on the filter output resets the history rather than publishing a bad value.
  - The renderer treats a non-finite attitude as facing the origin whether it came from a tracker or from the manual parameters: the RT stage does not get to trust its sources, and `juce::jlimit` passes NaN straight through, so a corrupt project file reaches the same code. Yaw wrapping also moved from a subtract-until loop to `fmod` — the unwrapped yaw accumulates without bound over a long show, which would grow the loop count on the tracker's callback thread.
- **Enabling binaural with no audio device open crashed the app.** The enable path skipped `prepareToPlay` when `getCurrentAudioDevice()` was null but started the worker anyway, which ran its block loop straight into null output rings (`LockFreeRingBuffer::write` on a null `this` — first field report came with exactly that stack). Fixed at two layers: the enable path now refuses without a device, logs once, and retries every tick so binaural comes up the moment a device runs; and the worker gates on a `prepared` flag, so any future out-of-order enable is silent instead of fatal. The hole predates the HRTF work — the legacy path had it too.
- **Every hardware channel above 128 was unreachable, on every path.** The patch window's diagnostics were the visible symptom — on a large rig the input matrix never lit up for an incoming signal and the output test tone was inaudible — but the same defect silently dropped *audio*. `MainComponent` is a `juce::AudioAppComponent`, so its callback was JUCE's `AudioSourcePlayer`, which holds `float* channels[128]` and stops compacting once those arrays are full. Anything indexing the buffer by hardware channel number therefore bounds-checked those channels away: the input metering, `applyInputPatch`, `applyOutputPatch`, the binaural direct outs and the test signal. Meanwhile the patch matrix offered columns up to `maxHardwarePatchChannels` (512) and marked them available, so the UI invited routing to channels the audio path could not reach — the failure looked like a broken test feature rather than a routing wall.
  - The app now drives **`spatcore::io::DeviceIoCallback`**, registered with `deviceManager.addAudioCallback`, in place of the `AudioAppComponent` player. It has no cap, and its buffer is indexed by **hardware channel** — which every one of those call sites already assumed. Buffer assembly mirrors `AudioSourcePlayer` (alias the device's output storage, pre-fill from the input, scratch rows elsewhere), so for a contiguous channel mask the source sees a byte-identical buffer. **The 15 offline-render baselines match unchanged**, which is the evidence that the DSP algorithms did not move — that harness drives the DSP headers directly and never instantiates a device callback, so the buffer assembly itself is evidenced by running the app on real hardware, not by the baselines. `AudioSourcePlayer`'s gain stage is not reproduced — it is a verified no-op at unity, the only gain `AudioAppComponent` ever set.
  - `attachAudioCallbacksIfNeeded()` no longer calls `setAudioChannels()`. That call re-opened the device to install the player and, in doing so, re-derived the channel counts from the current setup and froze them as `AudioDeviceManager`'s "channels needed" — the mechanism behind the second half of this bug.
  - **Scope caveat — not verified above 128 channels on hardware.** The dev machine's ASIO drivers (Dante Virtual Soundcard, MADIface, DiGiCo) are installed but none opens without its hardware or service, so the >128 path rests on the unit tests plus a 64-channel real-device run. A large rig should confirm metering and a test tone on a channel above 128 before this is relied on in the field. What *was* verified on a real driver: all 64 channels open, the saved state carries explicit channel masks, the buffer is hardware-indexed at full device width, and a tone renders on the highest output.
  - `spatcore-tests` covers the index translation (contiguous / sparse / empty / clamped), the channel-mask policy, and the generator's pitch, protective ramp and seeded reproducibility. It does **not** drive `DeviceIoCallback` — that needs a live `juce::AudioIODevice`, which cannot be faked headlessly without reimplementing a backend.
- **"Enable all channels" did not enable all channels.** `DeviceSettingsPanel::deviceChanged()` and `enableAllChannels()` built full `BigInteger` masks and handed them to `setAudioDeviceSetup()`, but never cleared `useDefaultInputChannels` / `useDefaultOutputChannels`. While either flag is set, `AudioDeviceManager` **discards the caller's mask** and substitutes `range(0, numInputChansNeeded)` — a count frozen by the `setAudioChannels()` call above at whatever the *startup* device had. Selecting a larger interface mid-session therefore reopened it with the old, smaller channel count, and because a mask is only persisted when the flag is clear, `createStateXml()` wrote no `audioDeviceInChans` at all and the next launch started from the same wrong number. The bug was self-perpetuating and left no trace in the saved state.
  - Device open and restore now go through **`spatcore::io::DeviceHost`**, which writes an explicit mask with both flags cleared on every mutation, and replaces the magic `256` that had been scattered across four call sites with the 512-channel policy limit. Verified against a real driver: the saved `DEVICESETUP` XML now carries explicit `audioDeviceInChans` / `audioDeviceOutChans`.
  - `DeviceHost` also scans the device-type list before opening a named device. Without that, `AudioDeviceManager` takes a silent early exit on an un-initialised manager: it opens nothing and returns an **empty** error string. Caught by pointing the real code at a Dante Virtual Soundcard whose service was down — raw JUCE reported "Error connecting to Dante Virtual Soundcard Manager" where the app reported success.
- **The patch matrix advertised channels the device had never opened.** Its "active" counts came from `device->getInputChannelNames().size()` — the channels the interface *lists* — so with a truncated mask the matrix rendered dead columns as fully patchable and testable. They now come from the channels actually opened (`getActiveInputChannels()`), so what the matrix offers is what the audio path can reach.
- **Three things made all of the above invisible to the operator.** A rejected test click returned silently; nothing was listening to the patch tabs' `onStatusMessage`, so even the existing "choose a test signal" message went nowhere; and a Tone was silent until something happened to call `setFrequency()`, because the phase increment defaulted to zero and `prepare()` never set it. A rejected click now names the channel that is not open, on the mouse and keyboard paths both, the status pipeline is wired to the status bar, and `prepare()` recomputes the phase increment — which also fixes the tone coming back at the wrong pitch after a sample-rate change.

That gap mattered little while every parameter also had a listed tool; with the catalog curated it would have been the primary write path. ## v1.0.0beta39 — 2026-07-26

### Changed
- **New inputs now default to 1.5 m height instead of 0 m** (`inputPositionZDefault`). Zero put every new source on the floor, which is neither where a performer nor a typical spot source actually is, so the height had to be dialled in by hand on every channel of every new session. 1.5 m is roughly a standing head. The value is absolute rather than origin-relative — the same convention as `ReverbNodePlacement::kDefaultHeight`, and the reason `getDefaultInputPosition` ignores `originH` while it does subtract `originW`/`originD` from X/Y. Existing sessions are unaffected: they store explicit positions, and this only feeds the from-scratch creation path and the engine-owned redistribute-on-count-change path.
- **Input Height Factor now defaults to 100% instead of 0%** (`inputHeightFactorDefault`). At 0% the Z difference was scaled out of the distance calculation entirely, so a source's height had no effect on what was rendered — which, combined with the old 0 m default, meant height was doubly inert out of the box. 100% takes elevation fully into account. Together with the change above, a new session now renders source height meaningfully by default rather than after two deliberate edits. The Set All Inputs window's dial and readout derive their initial value from the constant rather than the hardcoded `0` they carried, so the three stay in step.
- **The default window size is now clamped to 16:9 on ultrawide displays.** The size was 90% of the screen in *both* axes, so a 32:9 monitor opened the app as a ~3.5:1 letterbox strip — a shape the tab layouts were never designed for, and one that puts a screen-width of mouse travel between controls that belong together. Height still drives off 90% of the screen; width is now additionally capped at `height × 16/9`. Only displays wider than 16:9 are affected — on 16:9 and 16:10 the cap never binds and the default size is unchanged — and the window remains freely resizable, so the full width is still one drag away.
- **CPU SDN reverb is now node-parallel** (was strictly single-threaded). The per-sample lockstep is replaced by a chunked node-parallel sweep: within a window of C samples where every *effective* inter-node delay exceeds C, no node can read a delay-line cell another node writes in that window, so the nodes are independent across the whole window rather than only per sample. C is derived per block from the actual geometry — `min over paths of min(D, MAX_DELAY − D)`, using the shorter tap while a path crossfades — and collapses to 1 (reproducing the old lockstep exactly) for degenerate geometry. **Bit-exact**: all 15 CPU goldens pass unchanged, and hashes are identical across 0/3/7/15 workers. Measured at 32 nodes / 48 kHz / 256-sample blocks: **0.935 → 0.460 ms per block (~2×)** on 7 workers, against a 5.33 ms budget. `SDNAlgorithm::setParallelFor` was an empty override, so SDN had been silently ignoring the worker pool the engine already handed it — no engine change was needed to switch it on.
  - Two aliasing hazards the naive form misses are handled explicitly and documented in `chunkSamplesForBlock()`: the crossfade **dual-tap** (both old and new delays are live for ~10 ms after any geometry or `sdnScale` change) and **ring wraparound** (a read at `(base+s−D) mod 8192` aliases a write at `base+s'` once D approaches the 8191 clamp, ~14.3 m at `sdnScale` 4). The old lockstep was immune to the second by program order; a parallel sweep is not.
  - Note this shape was previously removed as buggy (`c3e7ae2`) because sub-block delays made it racy — it returns here with the correct bound rather than an assumption.
- **GPU SDN reverb is now node-parallel on CUDA, and usable at 32 nodes** (it previously was not, on any card). The new `sdn_process_nodes` kernel launches `grid = numNodes, block = 32` — one block per node, so the network finally spreads across SMs instead of occupying a single one. Only the memory traffic is parallelised: the N−1 gather loads and the N−1 scatter read-modify-writes, one path per thread. The accumulations that fix the result (the incoming sum and the Householder output sum) keep their exact path order on a single thread, as does everything recursive across samples (diffusers, tone, DC blocker). Two intra-block barriers per sample.
  - The incoming vector also moved from a per-thread `float[32]` into **shared memory**. A runtime-bounded loop indexes it, so it could never live in registers — the compiler was spilling it to local (global-backed) memory at a cost of N−1 stores and 2·(N−1) loads per node per sample, on top of the gather itself. That spill, not the barrier alone, was a large part of the cost.
  - Measured at 32 nodes / 48 kHz / 256-sample blocks (5.33 ms budget), median/max launch: **RTX 5070 4.52/4.84 → 0.319/0.421 ms (14.2×)**, **Tesla T4 7.01/7.18 → 0.426/0.565 ms (16.4×)**. The T4 goes from 131% of budget to 8%, so GPU SDN at 32 nodes stops being the thing that destabilised the direct WFS path — and on the T4 it is now cheaper than the CPU path while leaving the CPU free.
  - **Bit-exact**: all 15 GPU goldens unchanged on both sm_120 and sm_75, including the `moving` scenario that exercises the crossfade dual-tap. Unchanged hashes are the proof, not a re-baseline.
  - On the GPU a chunk boundary must be a **kernel-launch** boundary (the grid-wide barrier), since `__syncthreads()` only orders one block. The host therefore picks the mapping per block, and the original lockstep kernel is **retained** and selected automatically whenever the geometry is too tight for a parallel window — including before any geometry has arrived, where the delays are still 1. `WFS_SDN_TRACE=1` logs which mapping is live; `WFS_SDN_NODE_PARALLEL=0` forces the lockstep.
  - `CudaSdnBackend::prepare()` now runs a **warmup launch through both kernels** and then wipes the state back to pristine, so the first audible block is bit-identical to a prepare() that never warmed up. Both are needed, not just one: a session starts pre-geometry with every delay at 1, so it opens on the lockstep and only switches to the node-parallel kernel once real geometry arrives — which would otherwise pay a *second* first-launch stall mid-session, with audio already running. **Field-confirmed 2026-07-25**: after the reshape the T4 SDN pump dropped sharply and was stable, with the only remaining xruns at initialisation — which is what this removes.
  - **All three vendors now carry the reshape.** CUDA landed first, the HIP twin followed (`c12f3b6`, with the `WFS_SDN_TRACE` mapping log in `3da516a`), and the Metal twin after that (`a2f1ae4` — `numNodes` threadgroups × 32 lanes). All three are ancestors of the pinned spatcore `d1e6f66`, so this release ships node-parallel SDN on NVIDIA, AMD and Apple alike, each retaining its `grid = 1` lockstep for geometries too tight for a parallel window and each honouring `WFS_SDN_NODE_PARALLEL=0` / `WFS_SDN_TRACE=1`. Measured per vendor at 8 nodes: Windows × CUDA 2.1×, Windows × HIP 2.2×, Linux × HIP 2.4× on launch time, with the SDN peak identical across mappings (0.0633 on both vendors) — timing moves, arithmetic does not.
- The `Reverb GPU pump:` log line now records **which GPU the reverb backend is bound to**. The reverb and the direct-sound path can sit on different devices, so without it a reverb overrun could not be attributed between GPU co-tenancy and host contention — precisely the ambiguity that blocked the 2026-07-25 SDN investigation.

### Added
- **Position ownership rule** — automatic placement now runs until the user takes over, and never again afterwards. A single persisted, one-way latch (`positionsUserOwned`, on the Stage section, so it travels inside the session file) answers "may the engine still move channel positions?":
  - **Engine-owned** (fresh session, nothing touched): changing the channel counts, or the stage size/shape/origin, silently re-runs the **initial** placement for inputs *and* reverb nodes — both layouts depend on the totals and the stage, so channels created under an earlier count otherwise sit on the wrong grid/arc. Origin changes keep using the delta-shift, which for engine-placed nodes *is* the initial placement re-expressed in the new coordinates, and is the only correct move for outputs (physical speakers must keep their world position).
  - **User-owned** (the Map tab has been opened, or any input/output/reverb position edited): nothing repositions automatically. The explicit scale / fit-to-stage buttons take over, exactly as before.
  - The latch is set inside the parameter setters on position IDs only, so every user-facing path trips it — UI tabs, Map drags, OSC, MCP — while the engine's own layout helpers write via `setProperty` and bypass it. It is deliberately **not undoable**: Ctrl+Z must not re-arm auto-placement. A stage **shape** switch now counts as a placement event too (the layout is shape-dependent: grid bounds, semi-ellipse vs ring), which it previously did not.
  - Replaces the ephemeral visited-flags, which had both failure modes: they **forgot across restarts** (reloading a positioned show re-armed auto-placement on it), and they **false-tripped on a mere Inputs-tab visit** — looking is not positioning. Session files predating the property load engine-owned, matching the previous load behaviour.
- **Default reverb node placement** (`Source/Helpers/ReverbNodePlacement.h`). Reverb nodes previously defaulted to a straight line along X at 1 m spacing with Z = 0 — collinear, on the floor, and mirror-symmetrical about the centre. That is also where the degenerate SDN geometry came from: nodes a metre apart give inter-node delays of ~140 samples, well under the 256-sample internal block, so the node-parallel sweep collapsed to its per-sample lockstep window on a freshly created session. The default is now a **semi-ellipse** (box stages) or a **full ring** (cylinder/dome) at **1.5× the stage extent**, at a **2 m working height**.
  - Symmetry is broken by a jitter of **5% of the stage dimension per axis**. The jitter is **deterministic** (a hash of node index and axis), not `rand()` or a time seed: reverb positions feed the DSP — feed angular attenuation and the perceived return position — so a layout that differed run to run would make the same session render differently and would put nondeterminism into a golden-checked path. A hash is equally asymmetric for this purpose and is reproducible.
  - **De-crowding is on Z only.** Height is the perceptually cheapest axis to move a reverb node, so a user who stacks nodes gets a result that stays close to transparent while the inter-node distance — which is 3-D — recovers the margin the parallel sweep wants. The minimum spacing is derived rather than chosen: **2 m is one 256-sample block at 48 kHz** (256/48000×343 = 1.83 m), rounded up.
  - The height band is clamped to **0.5–8 m**, and that bound is load-bearing: 32 nodes on a small stage cannot all be 2 m apart on the arc, and an unbounded relaxation answers that by flinging nodes to absurd heights. Inside the band the pass does what it can and stops. Partial separation still helps — the chunk bound is recomputed per block from the real geometry, so it takes whatever margin exists, and the lockstep stays correct when there is none.
  - Axis note: X and Y are the floor plan (what the Map tab edits), **Z is height**. The old default's `Y = 2.0` was 2 m of *depth*; the nodes sat at Z = 0.
  - **Scope**: landed as creation-path-only and was then completed within this same release, so the caveat no longer applies. The ownership rule and both re-placement hooks are wired: a channel-count change re-runs placement at `WFSValueTreeState.cpp:1438` and `:1564`, and a stage size/shape/origin change at `SystemConfigTab.h:3373` and `:3394`, each guarded by `! arePositionsUserOwned()`. See *Position ownership rule* above for the latch that switches it off for good once the user takes over.
- **`offline-render --reverb-workers N`** — drives the CPU reverb paths' `AudioParallelFor` pool at a chosen width (default 0 = the sequential baseline the goldens are recorded against). Added to measure how the reverb algorithms scale with worker count and to verify their worker-count invariance; it is what disproved the 7-worker-cap hypothesis below.
- **CUDA graph submission for the GPU WFS gather path** (opt-in, `WFS_GPU_GRAPHS=1` read at engine start): the constant per-block core (input upload → both kernels → output download) is captured once into a CUDA graph at `prepare()` and replayed with a single `cuGraphLaunch` per block; the upload-diet/ping-pong matrix logic stays outside the graph, and the instantiated graph is pre-uploaded so the first block pays no lazy-init stall. **Bit-exact** (gather goldens hash identically with graphs on/off, verified on sm_120 and sm_75; kernel sources untouched — `kernel_hashes.py` clean). Measured at 96 kHz / 64-sample blocks, 64×128: on a compute-mode (MCDM) Tesla T4 this collapses the per-call submission stall tail — depth-1 underruns 82 → 5 per 30 s, p999 2.2 → ~1.0 ms; on the WDDM display RTX 5070 it is neutral (+~30 µs median), so the default stays off. Legacy path fully retained (the toggle doubles as the A/B switch); HIP twin port is a planned follow-up now the pattern is proven on NVIDIA; Metal needs nothing (already single-command-buffer submission).
- **`tools/validation/pipeline-bench`** — real-time latency/underrun harness. Unlike `offline-render` (synchronous, bypasses the async pipeline), it exercises the REAL `GpuAsyncPipelineT` — pump thread, SPSC rings, depth cushion, underrun accounting — driven by a metronomic simulated audio callback (high-resolution waitable timer + short spin to absolute deadlines, MMCSS-elevated). Reports per-depth underruns (pump-failure aware), backend-time distributions (min/med/p99/p999/max vs block budget), callback wake jitter, and a timestamped ≥1 ms spike log; `--depth-sweep 1..8`, `--json` output. Builds with `REVERB_DIAGNOSTICS=1`.
- **`Documentation/Windows_GPU_Latency_Tuning.md`** — measured runbook for the RTX 5070 + Tesla T4 rig: full depth-sweep tables (gather/scatter × both GPUs × legacy/graphs), per-device recommendations (**depth 3-4 is the safe operating point on either card**; 5070 graphs off; T4 graphs on **plus pinned clocks**; scatter and SDN reverb stay off the T4, FDN reverb is a good fit for it), a field-validated known-good split (WFS gather on the 5070 at depth 2 + 32-node FDN on the T4), clock-pinning / HAGS / MPO tuning steps, and the evidence-ranked optimization roadmap (OB graph path, HIP port, kernel occupancy split, prepare-time warmup launch).
- **Field finding — GPU SDN reverb does not scale past low node counts, on any card.** At 32 nodes the SDN reverb pump peaked at **7.5-9.4 ms against its 5.33 ms budget** (~25× the FDN pump's 0.35 ms at the same node count) and, while it ran, the direct WFS pump collapsed from ~0.2 ms to ~5 ms peaks with 2799 underruns in ~6 s; switching back to FDN restored normal operation instantly. Confirmed on the RTX 5070 as well as the T4 — this is the `sdn_process` `grid = 1` shape (one SM on any GPU, plus a per-sample `__syncthreads()` serial chain), so no GPU upgrade fixes it. The runbook now directs high-node-count SDN to the **CPU** SDN path (which spreads nodes across the `AudioParallelFor` pool) and adds a multi-block SDN kernel redesign to the roadmap, alongside a request to log the reverb backend's bound device (its absence made the episode impossible to attribute between GPU co-tenancy and host contention).
- **Field finding — 32-node SDN runs acceptably on the CPU path** (holds "most of the time" on a 9950X, with occasional dropped-reverb-block warnings), confirming the GPU→CPU redirect above. Measured follow-up **rejected** the initial hypothesis that `ReverbEngine.h`'s 7-worker pool cap was the constraint: `ReverbSDNAlgorithm::setParallelFor` is an empty override (SDN runs a synchronous node-lockstep by design — that is what makes it bit-exact with the GPU backend), so SDN never uses the pool and shows *zero* scaling from 0 to 23 workers; FDN scales well but saturates almost exactly at 7 (156 → 149 ms from 7 to 23 workers), so the existing cap is well chosen. **32-node SDN uses ~1.05 ms of its 5.33 ms budget single-threaded (~20%)**, so the residual dropped-reverb-block warnings are jitter, not throughput — CPU idle/power-state tuning is the fix and no code change would help. Also measured: at 32 nodes the CPU beats the GPU for both algorithms (SDN 1.05 ms CPU vs 7.5-9.4 ms GPU peak; FDN 0.20 ms vs 0.35 ms), so GPU reverb at this node count buys offload rather than speed. Worker-count hash invariance verified for both algorithms across 0/3/7/15/23 workers. The runbook also gains a CPU-side tuning section: AMD BIOS *Power Supply Idle Control → Typical Current Idle* + *Global C-state Control → Disabled* (the exact analogue of the GPU P-state finding), Windows minimum processor state 100%, and a note that CCD placement is entirely unmanaged (no affinity pinning exists anywhere in the app).
- **Measured 2x2 — clock pinning and CUDA graphs are redundant, not additive.** T4 gather, post-warmup underruns summed over depths 1-6 (30 s each): free clocks + legacy submission **211**, free + graphs **30**, pinned + legacy **28**, pinned + graphs **25**. Either intervention alone delivers ~7x; both together add almost nothing, so they attack substantially the same stall population (collapsing five submissions per block into one also removes most of the idle→busy transitions that invite power-state churn). Pinned + legacy was the only cell to reach **zero** underruns (depths 5-6). Medians move barely at all (0.174-0.201 ms across every cell) — all of it acts on the tail. Practical consequence: **pin the clocks and `WFS_GPU_GRAPHS` becomes optional on the T4.** Documented with explicit caveats: only the pinned pair is a strict back-to-back A/B, and the mechanism behind the field "max power" setting is unconfirmed (idle `nvidia-smi` read P0/1590 MHz both before and after it).
- **Measured — CPU affinity/CCD placement is not a first-order concern for this workload.** FDN 7-worker pool over 32 nodes under process affinity masks: all 32 logical CPUs 159.6 ms, one CCD 158.2 ms (within noise), one thread per physical core 153.2 ms (~4%, i.e. SMT-sibling contention, not CCD locality). At 0.20 ms of a 5.33 ms budget none of it is operationally relevant. The runbook additionally records why the thermal/boost-vs-cache-locality trade-off does not bind here (~20% duty cycle never saturates a core, so core rotation buys no boost headroom) and warns that pinning to a non-CPPC-preferred core set can *cost* a boost bin.
- **Field finding — GPU clock pinning is the highest-value knob, especially on compute cards.** Real-time audio at 96k/64 is a ~28% duty cycle, so the GPU goes idle thousands of times a second and default power management churns P-states, paying clock-ramp latency on the next block. Forcing the Tesla T4 to maximum power / locked clocks dropped its pump time considerably — to roughly RTX 5070-comparable — which no code change had achieved. This is idle-driven P-state management, **not** thermal throttling. It is not free, though: pinned clocks hold pinned voltage, and the T4 then draws 38.8 W of 70 W at ~11% utilisation (62 °C with its blower at 95%) — the runbook documents raising the clock *floor* (`-lgc 1200,1590`) as a lower-heat alternative to pinning at the ceiling. The runbook's depth-sweep tables were recorded with free clocks and therefore understate the T4; they are now labelled as the unmanaged baseline. Correspondingly the T4's stall tail is attributed to *both* P-state oscillation and MCDM per-call submission overhead (which the graph work addresses), with the caveat that the two were measured against the same symptom at different times, so their relative weight is not cleanly separated.

- The staged `wfs_cuda.dll` in the Windows build output was **stale** (built 2026-07-06, predating the FR diffusion Max-prototype port and the SDN N-invariant output-gain fix) — the app loads whatever plugin DLL is present, so those two DSP changes were silently absent from GPU processing on this machine. Rebuilt from current sources; per-device GPU goldens re-recorded (`baselines/win-rig-5070-gpu.json`, `win-rig-t4-gpu.json`). The runbook now prescribes rebuilding the plugin after pulling GPU-touching commits.

- **Warmup launch in the CUDA OutputBuffer (scatter) backend's `prepare()`**: the first post-prepare `processBlock` paid a measured 25-85 ms lazy-init stall (deferred driver/allocation commit), surfacing as an underrun burst right after every engine (re)start. `prepare()` now runs one silent block on the setup thread, then restores pristine first-launch state (`reset()` + the `frBasePrev` bootstrap) so the first audible block is bit-identical to a fresh prepare — verified against the GPU goldens on both devices. Re-measured at depth 4: RTX 5070 scatter fully clean (0 underruns, no block-0 spike); Tesla T4 scatter 0 post-warmup underruns (was 226 per 30 s), with a residual ~8 ms first block (was ~83 ms) costing ~10 underruns in the first ~10 ms of audio.

- **The level meter window's GPU pipeline strip only appeared when the DIRECT path was on a GPU.** `updateGpuPipelineStats()` early-returned unless the main algorithm was `NativeGpuWfs`/`NativeGpuOutputBuffer`, so GPU reverb with WFS on the CPU showed no GPU telemetry at all — despite the reverb pump being exactly what that configuration needs to watch, and despite reverb-on-a-second-card being a setup the tuning runbook recommends. The two backends are selected independently, so the reverb pump is now sampled unconditionally and only the direct-pump sampling stays gated. Two distinct questions are now asked separately: `isGpuStripRelevant()` (anything on a GPU → show the strip) and `isGpuAlgorithmCurrent()` (direct path on a GPU → the per-channel CPU thread bars are meaningless). Conflating them would also have wrongly *hidden* the per-channel bars as soon as GPU reverb came on; they are now kept whenever the direct path is on the CPU. Stats still clear when nothing is on a GPU, so no stale numbers.
- **The GPU strip shifted the level meters.** It occupied its own row carved above the buttons, while `paint()` draws the section separator at a fixed `getHeight()/2` — so the strip appearing pushed the output meters up over the line. It now shares the controls row to the right of the buttons and carves nothing, which removes the coupling entirely. In the narrower row the status text yields to the bars rather than squeezing them: it appears only once the four cells have their minimum width.
- **`HipSdnBackend`'s host-side params struct was left behind by the CUDA SDN reshape.** HIP compiles `CudaSdnKernels.h` **verbatim**, so the two new fields (`sampleOffset`, `chunkSamples`) were not a build error but a silent struct-layout mismatch — the kernel would have read its sample count off the end of the host struct. Fixed, and the full node-parallel mapping ported alongside it (both kernel handles, per-block selection, chunked launch loop, warmup, `WFS_SDN_NODE_PARALLEL`). **Since validated on real AMD hardware**, so this is no longer compile-verified only: 7/7 on a Radeon 780M (gfx1103) under ROCm 7.1 on Windows and under ROCm 7.1.1 on Linux, with the SDN peak identical across both mappings at 0.0633 — matching CUDA exactly — and launch time improving 2.2× on Windows, 2.4× on Linux. The retuning concern was well founded but did not bite: `block = 32` is one warp on NVIDIA, half a wavefront on GCN/CDNA and a full one on RDNA, yet the shape held on gfx1103 with no adjustment.
- **`build-gpu-plugins.ps1` skipped the HIP plugin on a machine that had the SDK installed.** Detection gated on `Get-Command hipcc`, i.e. on hipcc being on `PATH`, but the Windows HIP SDK installer sets `HIP_PATH` without adding its `bin\` — so the script reported "hipcc not found". Detection now resolves the SDK by root (`HIP_PATH`, then hipcc's own location, then the newest `C:\Program Files\AMD\ROCm\*`) and logs which root it picked.

- **The "CPU SDN is bit-for-bit identical to the GPU" contract is FALSE**, and had never been machine-checked — it was asserted in comments and in `core-boundary-proposal-audio.md`, and was the stated reason the CPU SDN ran a synchronous per-sample lockstep. Measured for the first time (same scenario, identical arguments, CPU `reverb-sdn` vs CUDA `gpu-reverb-sdn`): **94% of samples differ**, max abs diff **2.8×10⁻⁷** (**−123 dBFS** relative to peak), RMS **5.7×10⁻⁸**. That is float32 epsilon accumulated through a recursive network, so the algorithms do agree — their floating-point *association* does not, and no lockstep can fix that: NVRTC contracts to FMA and per-architecture codegen differs, which is why **sm_120 and sm_75 do not match each other either** and why the GPU goldens have always been recorded per-device. The real contract is **numerically equivalent to within float32 rounding**, not bit-identical; the docs now say so. Note this also means the lockstep was never buying the parity it was justified by — the node-parallel sweep gives up nothing that existed.
- **Ctrl-mirroring reverb nodes on the Map tab used the wrong axis and could merge a pair.** At all three sites (mouse drag, touch drag, keyboard nudge) the partner was written as `−x`, which reflects about x = 0 — but stored positions are origin-relative and the origin need not be the stage centre, so a non-zero `originWidth` threw the partner off to one side. Worse, near the axis the pair collapsed onto the same point, which for SDN means an inter-node delay of a few samples and a chunk window of 1. The axis is now the stage centre (`−originWidth`), and the offset is held to half the minimum spacing so a pair can approach the centre line without meeting. The dragged node is clamped as well as its partner — clamping one alone merely lets the other converge on it.
- **`ReverbAutoLayoutTool`'s generators had no minimum-spacing guard**: they place by angle, so a high node count on a small radius crowds nodes arbitrarily close. `applyLayout` now runs the same de-crowding pass as the default placement, on the same axis (separate in Z, leave the operator-visible plan untouched), reusing `ReverbNodePlacement` rather than open-coding a second rule.

## v1.0.0_beta1 — 2026-04-06

This release covers the entire foundational build-out of WFS DIY, from initial project scaffolding through 546 commits to the first beta tag.

### Foundation & Architecture
- Established the core multithreaded N-to-M WFS audio engine, with configurable delay/level routing, CPU monitoring, and dual-algorithm processing refactored into dedicated wrapper classes.
- Introduced a ValueTree-based parameter system underpinning config save/load, snapshots, and per-channel state throughout the app.
- Explored GPU-Audio SDK integration for offloaded processing (later disabled to unblock the build) and added a dedicated WFS input buffer processor architecture.

### Core GUI & Tabs
- Built out the main tabbed interface from scratch — Config/System Config, Network, Input, Output, Reverb, and Audio Interface & Patching tabs/windows — consolidating what were originally separate preview windows into one main window.
- Added the interactive Map tab (2D stage view with drag, multi-select, rubber-band, secondary-touch rotation/Z, keyboard nudging) and Clusters tab for grouping and moving multiple inputs together with shared LFO/scale/rotation.
- Delivered a unified color scheme system (Default, OLED Black, Light themes), proportional UI scaling for 4K and other resolutions, and extensive layout, spacing, and alignment polish across every tab.
- Added Gradient Map and StreamDeck+ Gradient Map systems for layer/shape-based parameter control with vertex/handle editing.

### WFS & Movement DSP
- Implemented the core WFS delay/level/HF calculation matrix and the Wizard of OutZ speaker-array design helper.
- Added Floor Reflections processing, Live Source Tamer feedback prevention, Input Speed Limiter (tanh smoothing), Sidelines automatic edge muting, and Flip X/Y/Z position mirroring.
- Added AutomOtion input-position automation (polar/cylindrical/spherical modes, audio-triggering, path recording, stage-aware repositioning) and LFO-based position modulation for both individual inputs and clusters.
- Added cylindrical/spherical/box/dome stage shape types with center-referenced coordinates and distance constraints.

### Reverb Engine
- Built the ReverbEngine from the ground up, implementing all three algorithms — FDN, SDN, and IR convolution — with pre/post-processing DSP, per-node parallelization, and crossfaded algorithm switching.
- Hardened IR convolution with non-uniform partitioning, buffer trimming/dynamic ranges, two-phase (silent-hold) loading, and dropout handling; added compressor/expander and gain-reduction metering, and fixed numerous reverb crash and state-persistence bugs.

### Binaural Renderer & Sampler
- Added the Binaural Renderer with solo monitoring, studio preview mode, and a custom rotation-dial UI, later moved off the audio callback for performance.
- Added a Sampler engine with grid/sets/pressure mappings, snapshot scope integration, and ROLI Lightpad-driven transient triggering.

### Networking, OSC & Remote Protocol
- Built the OSC networking stack: an OSCQuery discovery server (spec-compliant, WebSocket LISTEN support), source/sender-IP filtering, a network logging window, and QLab cue export/network integration.
- Added tracking-protocol support: generic OSC tracking, PSN (PosiStageNet), RTTrP, and MQTT, plus a 1-Euro adaptive smoothing filter for tracking input positions.
- Implemented the Remote control protocol end-to-end (handshake/heartbeat, full state dump and resync on reconnect, coalesced/rate-limited updates) along with ADM-OSC mapping (interactive Cartesian/Polar panels) and an Android remote app with a visual grid UI as an alternative sampler controller.
